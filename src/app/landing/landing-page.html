Five ideas to know first

  1. What an implementation guide and a profile are

    FHIR defines about 150 general-purpose resources, such as Patient and Observation, meant to be adapted. An implementation guide is a set of those adaptations, published as one unit. Each adapted resource is a profile: a set of constraints saying which elements are used, what's added, and which terminologies apply.

  2. Almost every US guide builds on US Core

    In the US, US Core sets the floor: the minimum constraints on the core resources, updated each year to follow USCDI. Of the US guides here that publish an R4 package, nine in ten depend on it, so it's the one to learn first.

  3. Some guides move data and others define it

    Some guides define what a record holds, like US Core for clinical data or CARIN Blue Button for claims. Others define how data moves: SMART App Launch for how an app signs in and gets permission, Bulk Data for exporting many patients' records at once. A project often needs one of each.

  4. Regulation drives much of what's adopted

    In the US, a rule is often the reason a guide gets built. ONC certification's (g)(10) API is built on US Core, SMART App Launch and Bulk Data. CMS-0057-F requires health plans to run Patient Access, Provider Access, Payer-to-Payer and Prior Authorization APIs, and recommends the Da Vinci and CARIN guides for them.

  5. Published isn't the same as used

    Two in three guides here are Standard for Trial Use (STU): ready for production, in HL7's words, but not yet in widespread use. The official registry still lists guides that were withdrawn, such as Patient Reported Outcomes. Before you build on a guide, check that the systems you exchange with support it.

Read first

  1. US Core: the home page, then General Guidance, then two profiles, Patient and Laboratory Result Observation. Not the whole guide.
  2. A first build: a plain Questionnaire and its completed form, QuestionnaireResponse. The result is a form on screen.
